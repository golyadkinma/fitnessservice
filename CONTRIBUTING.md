# Соглашения команды FitTrack

## Модель ветвления

Принята упрощённая модель GitFlow: постоянные ветки `main` (стабильный релизный
код) и `develop` (интеграционная ветка спринта), временные ветки задач:

- `feature/<задача>-<описание>` — разработка функции, создаётся от `develop`;
- `bugfix/<задача>-<описание>` — исправление дефекта, создаётся от `develop`;
- `hotfix/<описание>` — срочное исправление в релизе, создаётся от `main`.

Ветка `main` защищена от прямой записи: изменения попадают в неё только через
pull request. Слияние выполняется с флагом `--no-ff`, чтобы в истории
сохранялся факт существования отдельной ветки задачи.

Имя ветки строится по шаблону «тип/код-задачи-краткое-описание»,
например `feature/FT-02-bmi`.

## Сообщения коммитов

Применяется соглашение Conventional Commits:
`тип(область): краткое описание в повелительном наклонении`.

Типы: `feat` — новая функциональность, `fix` — исправление дефекта,
`refactor` — изменение кода без изменения поведения, `test` — работа с тестами,
`docs` — документация, `chore` — служебные изменения.

## Порядок код-ревью

1. Автор создаёт pull request из ветки задачи в `develop` с описанием:
   номер задачи, что сделано, как проверить.
2. Team Lead назначает рецензента из числа участников, не участвовавших
   в разработке.
3. Рецензент проверяет изменения по чек-листу, комментарии оставляет
   к конкретным строкам кода.
4. Автор отвечает на каждый комментарий: исправление или обоснование отказа.
5. После снятия блокирующих замечаний рецензент подтверждает изменения.
6. Автор выполняет слияние в `develop`.

Уровни замечаний: `blocker` (без исправления слияние невозможно),
`major` (исправить или обосновать), `nit` (на усмотрение автора).

## Чек-лист рецензента

- поведение соответствует описанию задачи и критериям приёмки;
- граничные случаи покрыты тестами, `go test ./server` проходит локально;
- отсутствует дублирование логики и числовые константы без пояснения;
- экспортируемые функции снабжены комментариями о назначении и ограничениях;
- ошибки обрабатываются явно, пользователь получает понятное сообщение;
- в клиентском коде не осталось отладочных вызовов `console.log`;
- при изменении API обновлён раздел «Маршруты» в README.md.

## Определение готовности задачи

Задача переводится в колонку Done, когда выполнены все условия:

1. код влит в ветку `develop`;
2. модульные тесты на новую логику написаны и проходят;
3. блокирующих замечаний ревьюера не осталось;
4. функция проверена вручную в интерфейсе приложения;
5. при изменении API обновлён README.md.

## Локальная проверка перед pull request

```
go build ./...      # сборка без ошибок
go vet ./...        # статический анализ
go test ./server    # модульные тесты
go run ./cmd/fittrack  # ручная проверка в браузере
```
